What does Transformer attention actually compute?

Core answer

Attention forms a content-dependent weighted combination of visible information; shapes, scaling and causal masks matter as much as the formula.

Reasoning & implementation

  1. Project input X into learned Q, K and V. QKᵀ scores each query against candidate positions; divide by √d, apply softmax over candidates and multiply by V. Q and K determine weights while V supplies content. They are projections, not three databases.

  2. Scaling controls the growth of dot-product magnitudes and helps avoid saturated softmax. Autoregressive attention masks future positions before softmax. Multiple heads aggregate relationships in different subspaces, without guaranteeing stable human-readable roles for each head.

  3. The ordinary full-attention relation matrix grows quadratically with sequence length. Longer inputs also make relevant evidence harder to select. Distinguish mathematical attention, efficient implementations and measured task quality instead of equating a larger window with reliable reasoning.

Engineering example

With X shaped [2,128,512], eight 64-dimensional heads produce weights shaped [2,8,128,128]. Changing future tokens must leave earlier outputs unchanged; this catches a reversed causal mask.

Follow-up

Follow-up: Why not mask after softmax? Answer: That discards probability mass and changes output scale unless renormalized. Exclude unavailable positions before normalization.

Common pitfall

Do not treat attention weights as a complete causal explanation or forget padding masks.

Why does KV caching accelerate decoding and consume memory?

Core answer

KV caching reuses past keys and values during decoding, trading repeated computation for memory that scales with sequence length and concurrency.

Reasoning & implementation

  1. Prefill processes the prompt and constructs historical keys and values at every layer. Decoding then projects the new token and attends to cached history. Causality makes past states reusable, but new queries and the remaining forward pass still require computation.

  2. Approximate capacity is 2 × layers × KV heads × head dimension × cached tokens × bytes per element, then account for concurrency and allocation overhead. Use KV-head count: MQA and GQA share keys and values. Weights, activations and workspaces need additional memory.

  3. Separate time to first token from inter-token latency. Long prompts, outputs and concurrent requests can make the cache the dominant bottleneck. Evaluate paging, prefix reuse, quantization and context limits against realistic length distributions, tail latency and quality.

Engineering example

For 32 layers, eight KV heads, dimension 128, 4096 tokens and two bytes per element, cache memory is about 512 MiB per request, excluding weights and overhead.

Follow-up

Follow-up: Can users share caches? Answer: Only identical, safely reusable prefixes qualify, with isolation, versioning and eviction; semantic similarity is insufficient.

Common pitfall

Do not reuse training-memory formulas for inference or claim that cached decoding no longer depends on history length.

How do temperature, top-p and determinism affect agents?

Core answer

Sampling controls the output distribution, not factual correctness or authorization; validate actions independently at the tool boundary.

Reasoning & implementation

  1. Temperature rescales logits before probabilities are formed; lower values generally concentrate the distribution. Top-p restricts candidates to a cumulative probability mass and renormalizes. Implementation order can vary, so record model, parameters and API version.

  2. Tool arguments and classification often benefit from less variation; creative candidate generation may benefit from diversity followed by validation. Low temperature can produce the same false answer consistently. Greedy decoding is not a promise of identical output across serving changes.

  3. Measure correctness and stability separately through repeated trials: task success, disagreement, invalid actions and cost. If selecting from multiple candidates, include verifier cost and selection effects instead of attributing every gain to stronger underlying capability.

Engineering example

A restaurant agent can generate JSON with concentrated sampling, but dates still need normalization, cities need checking and payment needs authorization. Recipe ideation may use more diverse sampling.

Follow-up

Follow-up: Does temperature zero remove hallucinations? Answer: No. Missing evidence or incorrect context can still produce a deterministic error.

Common pitfall

Avoid changing multiple sampling controls without attribution or equating exact string agreement with business correctness.

How do embeddings and rerankers differ?

Core answer

Embeddings support efficient candidate retrieval, while rerankers usually use richer query-document interaction to reorder a smaller set.

Reasoning & implementation

  1. A dual encoder maps query and document independently, enabling precomputed document vectors and approximate nearest-neighbor indexing. Coordinates are learned latent features, not fixed labels such as price or sentiment.

  2. A cross-encoder reranker processes query-document pairs jointly and can model conditions or negation more precisely, but pays per candidate. Rerankers can use other architectures, so describe the actual implementation rather than defining the category by one design.

  3. Reranking cannot recover a relevant document missing from retrieval. Domain mismatch and truncation can also damage ranking. Measure recall, ranking quality and answer quality separately, then choose candidate counts from quality-latency curves.

Engineering example

A query about travel reimbursement during probation may resemble permanent-employee policy. Retrieve 60 passages, then rerank using employment and timing conditions before selecting evidence.

Follow-up

Follow-up: Is similarity confidence? Answer: Not directly. Calibrate thresholds on labeled data and separately assess whether evidence supports the answer.

Common pitfall

Do not confuse embedding retrieval with model memory or change query encoders without a compatible document index.

What do pretraining, SFT and preference optimization solve?

Core answer

Choose training stages from the failure mode: knowledge coverage, task behavior and preferences require different data and objectives.

Reasoning & implementation

  1. Pretraining learns broad patterns through large-scale sequence prediction. SFT uses demonstrations to teach formats, tool conventions and domain behavior. Include genuine input distributions and examples of clarification, inability and refusal where relevant.

  2. Preference optimization changes choices using comparisons or reward signals. It cannot automatically supply authoritative facts or replace permissions. Frequently updated knowledge often belongs in retrieval; persistent behavioral or format errors may justify training.

  3. Build a reproducible baseline and error taxonomy before comparing prompts, retrieval, SFT and preference optimization. Measure leakage, general-capability regression and deployment cost. Gains on training-like questions do not establish improved real-world performance.

Engineering example

If support answers omit a required refund field despite finding the policy, try constraints and examples before SFT. If yesterday's policy is absent, repair ingestion instead of retraining.

Follow-up

Follow-up: Can SFT and RL share data? Answer: They can share task sources, but SFT needs demonstrations and RL needs evaluable tasks and feedback, with different formatting and sampling requirements.

Common pitfall

Do not train and validate on contaminated copies of the same tasks or treat use of RL as evidence of maturity.

How does LoRA work, and when is QLoRA useful?

Core answer

LoRA represents weight updates with low-rank factors; QLoRA additionally reduces frozen-base storage, with quality and runtime tradeoffs.

Reasoning & implementation

  1. For W of shape d_out×d_in, LoRA uses ΔW=(α/r)BA with A shaped r×d_in and B shaped d_out×r while freezing W. It adds r(d_in+d_out) parameters. The low-rank assumption concerns the update, not necessarily the base matrix.

  2. Rank, target layers, scaling, learning rate and data quality interact. Adapting attention only differs from also adapting FFNs. Initialization commonly starts with a near-zero update. Weight merging and inference overhead depend on deployment and quantization constraints.

  3. QLoRA quantizes the frozen base while training adapters to reduce memory requirements. Activations, optimizer state and long sequences still cost memory. Compare equivalent datasets, budgets and evaluation protocols before accepting the quality-resource tradeoff.

Engineering example

A 4096×4096 projection with rank eight adds 65,536 parameters, about 0.39% of that matrix. This does not imply training memory falls to the same fraction.

Follow-up

Follow-up: Is larger rank always better? Answer: No. It can overfit or cost more without gains; choose using domain and general holdouts, not training loss alone.

Common pitfall

Frozen weights still participate in activation computation. Also verify adapter-base version compatibility.

How should you choose between DPO, PPO and GRPO?

Core answer

Choose based on available feedback, environment cost and failure structure: DPO uses preference pairs, while PPO and GRPO commonly optimize sampled behavior using rewards.

Reasoning & implementation

  1. DPO optimizes relative likelihoods of preferred and rejected answers, commonly against a reference, without the traditional separate reward-model-plus-PPO pipeline. Simplicity does not remove coverage gaps, length bias or inconsistent preferences.

  2. PPO constrains policy updates and uses advantage estimates, commonly involving value estimation. GRPO often derives advantages from relative rewards among samples of the same task, reducing reliance on a separate value model while retaining sampling cost and credit-assignment problems.

  3. Strong offline comparisons and expensive interaction favor evaluating DPO first. Verifiable tool outcomes may justify online reward optimization. Include fair baselines, environment cost, constraints and diagnostics rather than choosing by novelty.

Engineering example

Code repair with a trusted test sandbox can reward sampled patches. Open-ended summarization may have editor comparisons instead. Both need protection against learning evaluator shortcuts.

Follow-up

Follow-up: Must DPO increase every preferred answer's absolute probability? Answer: No. Relative preference objectives do not guarantee that; inspect length, reference drift and actual outcomes.

Common pitfall

Do not confuse PPO probability-ratio clipping with gradient clipping.

How do GRPO group rewards, credit assignment and reward hacking interact?

Core answer

Group-relative rewards provide comparative signals, but do not identify every responsible action in a long trajectory; inspect both outcomes and behavior.

Reasoning & implementation

  1. A common GRPO formulation samples several responses to one task and forms advantages from within-group reward statistics. A group of one, or identical rewards, degenerates the comparison signal. Adding epsilon prevents division errors, not loss of information; variants may use different baselines.

  2. In multi-tool tasks, terminal success may depend on early retrieval or later recovery. Applying a final reward across a sequence does not prove each action deserves credit. Process rewards help only when intermediate progress is verifiable rather than performative text.

  3. Monitor success, reward variance, length, entropy, KL, invalid actions and execution cost. Rising reward without real success suggests evaluator exploitation or shift. Use isolated evaluation, adversarial cases and human review to preserve the actual objective.

Engineering example

Rewarding search calls alone invites repeated searches. Verify evidence support and charge redundant calls, while retaining legitimate multi-search tasks so useful exploration remains possible.

Follow-up

Follow-up: What happens at group size one? Answer: Standard within-group centered advantages become zero; implementations with other baselines require separate analysis.

Common pitfall

Reward curves are not success curves, and additional process rewards can create additional exploitable proxies.

What makes a system an agent?

Core answer

The key is control: does the system select its next allowed action from the goal and observed environment? Chat history, one tool call, or an LLM alone does not establish an adaptive loop.

Reasoning & implementation

  1. Separate model from system. The model proposes outputs or actions; application code owns state, execution, authorization, and observations. Chatbots can retain history and workflows can call tools. Ask whether new evidence can change the execution path.

  2. An operational loop has a goal, observable state, an action set, and stopping conditions. Update facts after each action, then continue, reroute, escalate, or finish. Autonomy can be local: query selection may be adaptive while refund calculation and submission remain deterministic.

  3. Measure value against a fixed workflow using success, cost, latency, and unauthorized actions. Adaptive paths should handle real variation. If paths rarely differ, extra loops add failure points; changing environments provide a stronger reason for autonomy.

Engineering example

A support agent checks an order, then chooses warehouse records if returned or tracking if in transit. Refund execution still passes business validation.

Follow-up

Follow-up: Must an agent use tools? Answer: Some definitions permit internal environments; state your definition and demonstrate decisions, observations, and feedback rather than debating labels.

Common pitfall

Do not call all conventional LLM apps stateless or treat a completion claim as proof. Verify the observable outcome.

When should you use a workflow or an agent?

Core answer

Distinguish variable inputs from variable execution paths. Stable steps favor workflows; introduce agent decisions where runtime observations determine the next step. Hybrids often make risk and cost easier to control.

Reasoning & implementation

  1. List invariants such as identity checks, spending limits, and tenant boundaries. Enforce them in code and authorization. Identify uncertain stages—classification, evidence search, diagnosis—where model decisions or bounded loops are useful.

  2. A workflow can contain probabilistic model calls while application code owns transitions. An agent can be constrained by tools, steps, and failure exits. Consider failure consequences, environmental variability, verification quality, and human recovery.

  3. Compare equal task sets and budgets. Classify baseline failures and check whether adaptive decisions address them. If gains come from a larger model or budget, do not attribute them to agent architecture; use matched ablations.

Engineering example

An expense workflow fixes extraction, validation, approval, and posting, invoking an agent only to resolve missing evidence before returning to validation.

Follow-up

Follow-up: Why not make every stage agentic? Answer: Each decision expands the state space and test burden. Grant autonomy where measurable benefits justify it, with explicit fallback paths.

Common pitfall

Deterministic control does not eliminate service failures, and sensitive domains do not exclude every model decision. Constrain its influence precisely.

Why does ReAct help, and how do you prevent loops?

Core answer

ReAct alternates decisions, actions, and observations so later choices use real feedback instead of a guessed full trajectory. It supports correction but increases calls, context, and cumulative failure risk.

Reasoning & implementation

  1. Treat each model decision as a proposal. Validate tool, arguments, and authorization before execution. Return structured success, failure, or unknown status with provenance. Observations from webpages are data, not permission to change policy.

  2. Enforce step, time, cost, and tool budgets externally. Detect repeated arguments, repeated errors, and stalled progress. Switch strategies or escalate for a stated reason rather than cycling through tools around the same root cause.

  3. Evaluate outcome, efficiency, and authorization across the trajectory. Log tool requests, observation summaries, transitions, and stop reasons; private internal reasoning is not required for audit. Test control flow with replayable stubs, then evaluate real environments.

Engineering example

A documentation agent notices a version mismatch and retrieves the correct version. If evidence remains missing after bounded attempts, it reports the gap.

Follow-up

Follow-up: Is the model saying done sufficient? Answer: It can propose termination, but the host should verify artifacts or records against acceptance conditions.

Common pitfall

More reasoning text is not progress. Progress means new evidence, reduced uncertainty, or a verified subgoal.

How do you design an orchestrator–worker system?

Core answer

The orchestrator owns goals, dependencies, and acceptance; workers handle bounded tasks. Split around independent context, permission boundaries, or parallel work—not merely to increase the agent count.

Reasoning & implementation

  1. Define evidence inputs, output schemas, acceptance tests, budgets, and prohibited actions. Workers return provenance, failure status, and open questions. The orchestrator checks contradictions, dependencies, and overall completion instead of concatenating prose.

  2. Minimize shared state and disclose only necessary context. Use task IDs, evidence references, and result versions. Concurrent writes to one business object need a single committer or version checks; models do not provide a concurrency protocol.

  3. Persist task assignments, reclaim timeouts, and define reassignment because the orchestrator can bottleneck or fail. Measure worker quality and synthesis loss separately. Parallel speedups must account for coordination and merge costs.

Engineering example

A research orchestrator assigns read-only vendor studies with a common evidence schema, then reconciles conflicting pricing claims before synthesis.

Follow-up

Follow-up: Must every task restart after one failure? Answer: Retry failed tasks and affected dependents, preserving verified results; invalidate results whose shared inputs changed.

Common pitfall

More roles do not imply independent evidence. Identical models and sources can produce correlated errors.

13 / 96 · Agent architecture

How do framework, runtime, and harness differ?

Core answer

A framework offers building blocks, a runtime manages execution and recovery, and a harness packages the model loop, context, tools, and policy into a working system. These are responsibilities, not rigid product categories.

Reasoning & implementation

  1. Start from requirements rather than brands. Frameworks help compose models and tools; runtimes address durable tasks; harnesses provide operational defaults for tools, context, and permissions. One product may cover several roles, so verify capabilities individually.

  2. A harness controls observations, validation, error feedback, compaction, and termination—not just a prompt. Model behavior depends on those choices. Hold tool descriptions, budgets, retrieved data, and environments constant when comparing models.

  3. Before building, identify constraints such as audit, restricted networks, or domain state machines. Adapters may be cheaper than rewriting infrastructure. If hidden control flow violates requirements, own that portion explicitly and validate behavior with regressions.

Engineering example

A coding harness may manage file reads, patches, test-output limits, authorization, and recovery, while using a separate durable runtime and framework tool adapters.

Follow-up

Follow-up: Why can the same model perform differently? Answer: Tools, feedback, context, and budgets change its decision conditions. Use controlled ablations instead of universal attribution percentages.

Common pitfall

Frameworks can include loops and policy facilities. A harness does not guarantee safety without enforcement at execution boundaries.

How do state, reducers, checkpoints, and interrupts work together?

Core answer

Nodes read state and emit updates; edges select execution; reducers merge updates. Checkpoints persist recovery state and interrupts pause for external input. Recovery and duplicate side effects are separate design concerns.

Reasoning & implementation

  1. Separate goals, messages, progress, and results in the state contract. Parallel updates require merge rules. List concatenation may suit logs but not balances, unique task status, or messages updated by identity. Choose reducers from business invariants.

  2. Bind checkpoints to task or session identity and persist versions needed for recovery. Nodes may replay, so external calls need idempotency keys or completion records. Persisted graph state does not create an atomic transaction with payments or messages.

  3. Pause after a concrete action is prepared but before submission. Bind approval to that action version; on resume, recheck changed arguments or business state. Test denial, timeout, restart, and repeated resume as well as the happy path.

Engineering example

A refund flow pauses with a fixed order and amount. On recovery after a crash, it queries the business request ID before attempting submission again.

Follow-up

Follow-up: Must reducers be commutative? Answer: It depends on ordering semantics; prefer order-independent merges under concurrency, or impose ordering and test replay consistency.

Common pitfall

An in-memory checkpointer is not crash-durable storage, and pre-interrupt code may rerun. Verify replay semantics for the chosen version.

How does computer use differ from API-based agents?

Core answer

API agents operate structured interfaces; computer-use agents observe and manipulate interfaces. They reach systems without suitable APIs but must handle UI state, targeting, asynchronous change, and uncertain action completion.

Reasoning & implementation

  1. Perception may use screenshots, DOM, accessibility trees, or combinations. Structured references suit many web controls; vision covers canvases and desktop interfaces. Bind actions to fresh observations so stale coordinates or references do not target the wrong element.

  2. Use observe, locate, act, wait, and verify. Confirm object, amount, and authorization before consequential actions and inspect resulting records afterward. Timeout does not mean failure; check whether a submission succeeded before clicking again.

  3. Web content cannot grant permissions. Use isolated sessions, scoped credentials, and handoff paths. Measure mistargeted clicks, duplicate submissions, recovery, and time per success alongside completion. Prefer suitable stable APIs when available.

Engineering example

For procurement entry, identify fields, fill line items, verify the confirmation total, submit, and check the record ID. Refresh observations after navigation.

Follow-up

Follow-up: What about a CAPTCHA? Answer: Pause for the authorized human or site flow and preserve progress rather than attempting a bypass.

Common pitfall

A visible interface does not guarantee reliable automation; permissions, observability, complexity, and site restrictions still matter.

How do deep research and agentic RAG relate?

Core answer

Agentic RAG makes retrieval adaptive; deep research organizes an investigation and synthesis task. They can share retrieval loops. Scope, evidence management, and deliverable requirements matter more than fixed search counts or public-web access.

Reasoning & implementation

  1. Start with subquestions and coverage criteria, then retrieve, read, and extract. Keep source, date, location, and conditions for each claim. Track conflicting evidence and investigate it rather than deciding truth by source count.

  2. Stop based on evidence coverage and resource limits: supported core questions, resolved conflicts, or diminishing information gain. Disclose gaps if budgets expire. Report length and query counts are not sufficiency metrics.

  3. Synthesis links claims to evidence and separates facts, inferences, and recommendations. Evaluate citation support, source independence, freshness, and counterevidence. Agentic RAG can provide retrieval across private and public materials.

Engineering example

A migration study defines compatibility, downtime, rollback, and cost questions, combines official documentation with internal constraints, resolves version conflicts, then synthesizes a comparison.

Follow-up

Follow-up: How do you prevent endless searching? Answer: Track coverage and open questions, budget follow-up searches, and stop when results repeat or uncertainty cannot be resolved.

Common pitfall

Long reports are not inherently good research. Cite pages or passages that support specific claims, not merely a site homepage.

What belongs in a reliable agent system prompt?

Core answer

Define goals, boundaries, capabilities and completion criteria, while separating evidence from trusted instructions.

Reasoning & implementation

  1. State goals and completion criteria, then tool contracts and clarification conditions. Make constraints operational: never invent order IDs, check targets and authorization, expose evidence gaps. Abstract personality instructions are hard to test.

  2. Mark retrieved documents and tool output as data rather than authority. They can inform facts without changing permissions. Use concise plans, observable status and evidence, not private chain-of-thought disclosure, as verification artifacts.

  3. Reduce conflicts and redundancy and regression-test model changes. Enforce critical constraints in code, permissions and state machines; prompts guide choices but cannot guarantee safe side effects.

Engineering example

A refund assistant first checks order and policy, then proposes an action. The tool validates ownership and limits; 'refunded' requires confirmed tool success.

Follow-up

Follow-up: Are longer prompts safer? Answer: Not necessarily. Redundancy consumes context and creates conflict; retain testable constraints and load infrequent knowledge on demand.

Common pitfall

class LocalLedger:
    # Teaching example: single process, no concurrent callers.
    def __init__(self, balance):
        self.balance = balance
        self.completed = {}

    def debit(self, key, amount, lose_response=False):
        if key in self.completed:
            old_amount, result = self.completed[key]
            if old_amount != amount:
                raise ValueError("key reused with different payload")
            return result
        if amount <= 0 or amount > self.balance:
            raise ValueError("invalid amount")
        self.balance -= amount
        result = {"key": key, "balance": self.balance}
        self.completed[key] = (amount, result)
        if lose_response:
            raise TimeoutError("response lost after commit")
        return result

def debit_with_retry(ledger, key, amount):
    for attempt in range(2):
        try:
            return ledger.debit(key, amount, lose_response=(attempt == 0))
        except TimeoutError:
            if attempt == 1:
                raise
    raise AssertionError("unreachable")

if __name__ == "__main__":
    ledger = LocalLedger(100)
    result = debit_with_retry(ledger, "order-1", 20)
    assert result["balance"] == 80

import math

def causal_attention(q, k, v):
    # Single sequence, single head, equal query/key sequence length.
    n = len(q)
    if not n or len(k) != n or len(v) != n:
        raise ValueError("nonempty matching sequence lengths required")
    d, dv = len(q[0]), len(v[0])
    if not d or not dv:
        raise ValueError("feature dimensions must be positive")
    if any(len(row) != d for row in q + k):
        raise ValueError("Q/K feature dimensions must match")
    if any(len(row) != dv for row in v):
        raise ValueError("V rows must share a feature dimension")
    output = []
    for i, query in enumerate(q):
        # Only visible keys participate in softmax.
        scores = [sum(x * y for x, y in zip(query, k[j]))
                  / math.sqrt(d) for j in range(i + 1)]
        maximum = max(scores)
        weights = [math.exp(score - maximum) for score in scores]
        total = sum(weights)
        weights = [weight / total for weight in weights]
        output.append([
            sum(weights[j] * v[j][c] for j in range(i + 1))
            for c in range(dv)
        ])
    return output

if __name__ == "__main__":
    q = k = [[1.0, 0.0], [0.0, 1.0]]
    first = causal_attention(q, k, [[2.0], [8.0]])

    assert first[0] == changed[0] == [2.0]
